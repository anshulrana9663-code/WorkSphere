## 1. System Architecture Overview

WorkSphere is a **full-stack workforce management application** made of two separate projects inside one Visual Studio solution:

```
WorkSphere/
├── WorkSphere.Client/     ← React 18 + TypeScript + Vite (frontend SPA)
└── WorkSphere.Server/     ← ASP.NET Core 8 Web API (backend)
```

The two projects communicate over HTTP. The frontend never stores the JWT token in `localStorage`; it is kept in an **HttpOnly cookie** (`ws_auth_token`) managed entirely by the browser. This prevents XSS-based token theft.

A second **non-HttpOnly** cookie (`XSRF-TOKEN`) carries the CSRF token that the client reads via JavaScript and sends back in the `X-XSRF-TOKEN` header on every mutating request (POST/PUT/PATCH/DELETE), implementing the **Double Submit Cookie** pattern.

## 3. SQL Database — Tables & Relationships

The database is managed by **Entity Framework Core migrations**. There are three migration snapshots:

- `InitialCreate` — ASP.NET Identity tables + `Employees`
- `AddTaskTables` — `Tasks`, `TaskComments`, `TaskAttachments`
- `AddTaskReviewsAndEmployeeCRUD` — `TaskReviews`

### 3.1 Identity Tables (managed by ASP.NET Core Identity)

These are auto-generated by `IdentityDbContext<ApplicationUser>`:

| Table | Purpose |
|---|---|
| `AspNetUsers` | Login credentials (email, password hash, etc.) |
| `AspNetRoles` | Named roles: `Admin`, `Employee` |
| `AspNetUserRoles` | Many-to-many join: which user has which role |
| `AspNetUserClaims` | Per-user JWT claims |
| `AspNetRoleClaims` | Per-role JWT claims |

### 3.2 `Employees` Table

Configured by `EmployeeConfiguration.cs` → `builder.ToTable("Employees")`.

```sql
CREATE TABLE Employees (
    Id          INT             PRIMARY KEY IDENTITY,
    FirstName   NVARCHAR(50)    NOT NULL,
    LastName    NVARCHAR(50)    NOT NULL,
    Email       NVARCHAR(150)   NOT NULL UNIQUE,         -- Unique index
    PhoneNumber NVARCHAR(20)    NULL,
    JobTitle    NVARCHAR(100)   NOT NULL,
    Department  NVARCHAR(100)   NULL,
    HireDate    DATETIME2       NOT NULL,
    Salary      DECIMAL(18,2)   NULL,
    IsActive    BIT             NOT NULL DEFAULT 1,
    CreatedAt   DATETIME2       NOT NULL DEFAULT GETUTCDATE(),
    UpdatedAt   DATETIME2       NULL,

    -- Self-referencing FK: who manages this employee
    ManagerId   INT             NULL REFERENCES Employees(Id) ON DELETE RESTRICT,

    -- Link to ASP.NET Identity user (can be NULL for employees without a login account)
    UserId      NVARCHAR(450)   NULL UNIQUE REFERENCES AspNetUsers(Id) ON DELETE SET NULL
);
```

**Key design decisions:**
- `ManagerId` is a **self-referencing foreign key** — it points back to the same `Employees` table, enabling the org chart tree.
- `UserId` links to `AspNetUsers`. An employee record can exist without a login account (created by admin via `POST /api/employees`), or with one (created via `POST /api/auth/employees`).
- `IsActive = 0` is a soft-delete; the row is never physically removed, preserving task/review history.

### 3.3 `Tasks` Table

Configured by `WorkTaskConfiguration.cs` → `builder.ToTable("Tasks")`.

```sql
CREATE TABLE Tasks (
    Id            INT             PRIMARY KEY IDENTITY,
    Name          NVARCHAR(200)   NOT NULL,
    Description   NVARCHAR(2000)  NULL,
    AssignedById  INT             NULL REFERENCES Employees(Id) ON DELETE RESTRICT,  -- Who created/assigned
    AssignedToId  INT             NULL REFERENCES Employees(Id) ON DELETE RESTRICT,  -- Who must do it
    DueDate       DATETIME2       NULL,
    CreatedDate   DATETIME2       NOT NULL DEFAULT GETUTCDATE(),
    UpdatedDate   DATETIME2       NULL,
    Status        NVARCHAR(50)    NOT NULL,   -- Stored as string: 'Pending','InProgress','InReview','Completed','Cancelled'
    Priority      NVARCHAR(50)    NOT NULL    -- Stored as string: 'Low','Medium','High','Urgent'
);

-- Indexes for fast lookups
CREATE INDEX IX_Tasks_AssignedToId  ON Tasks(AssignedToId);
CREATE INDEX IX_Tasks_AssignedById  ON Tasks(AssignedById);
CREATE INDEX IX_Tasks_Status        ON Tasks(Status);
```

**Status enum values** (stored as strings in DB via EF Core `.HasConversion<string>()`):

| Value | Int | Meaning |
|---|---|---|
| `Pending` | 0 | Newly created, not started |
| `InProgress` | 1 | Assignee is working on it |
| `InReview` | 2 | Submitted for review by assignee |
| `Completed` | 3 | Manager confirmed done |
| `Cancelled` | 4 | Dropped |

**Priority enum values:**

| Value | Int |
|---|---|
| `Low` | 0 |
| `Medium` | 1 |
| `High` | 2 |
| `Urgent` | 3 |

### 3.4 `TaskComments` Table

```sql
CREATE TABLE TaskComments (
    Id          INT             PRIMARY KEY IDENTITY,
    Content     NVARCHAR(MAX)   NOT NULL,
    EmployeeId  INT             NOT NULL REFERENCES Employees(Id),  -- Author
    TaskId      INT             NOT NULL REFERENCES Tasks(Id),
    CreatedDate DATETIME2       NOT NULL DEFAULT GETUTCDATE(),
    UpdatedDate DATETIME2       NULL
);
```

### 3.5 `TaskAttachments` Table

Files are stored on disk under `wwwroot/attachments/{taskId}/{guid}{ext}`. The table stores metadata only.

```sql
CREATE TABLE TaskAttachments (
    Id              INT             PRIMARY KEY IDENTITY,
    Name            NVARCHAR(MAX)   NOT NULL,     -- Display name (without extension)
    EmployeeId      INT             NULL REFERENCES Employees(Id),  -- Uploader
    TaskId          INT             NOT NULL REFERENCES Tasks(Id),
    FileName        NVARCHAR(MAX)   NOT NULL,     -- Original file name
    StoredFileName  NVARCHAR(MAX)   NOT NULL,     -- GUID-based stored name on disk
    Size            BIGINT          NOT NULL,     -- Bytes
    Location        NVARCHAR(MAX)   NOT NULL,     -- Relative URL: /attachments/{taskId}/{storedFileName}
    UploadedDate    DATETIME2       NOT NULL DEFAULT GETUTCDATE(),
    ContentType     NVARCHAR(MAX)   NOT NULL
);
```

### 3.6 `TaskReviews` Table

```sql
CREATE TABLE TaskReviews (
    Id            INT             PRIMARY KEY IDENTITY,
    RevieweeId    INT             NOT NULL REFERENCES Employees(Id) ON DELETE RESTRICT,  -- Who is being reviewed
    ReviewerId    INT             NOT NULL REFERENCES Employees(Id) ON DELETE RESTRICT,  -- Who is writing the review
    StarRating    INT             NOT NULL,         -- 1 to 5
    Comment       NVARCHAR(4000)  NOT NULL,
    ReviewPeriod  NVARCHAR(50)    NOT NULL,         -- Free text e.g. "Q4 2026"
    CreatedAt     DATETIME2       NOT NULL DEFAULT GETUTCDATE(),
    UpdatedAt     DATETIME2       NULL
);

-- Indexes
CREATE INDEX IX_TaskReviews_RevieweeId ON TaskReviews(RevieweeId);
CREATE INDEX IX_TaskReviews_ReviewerId ON TaskReviews(ReviewerId);
CREATE INDEX IX_TaskReviews_RevieweeId_ReviewPeriod ON TaskReviews(RevieweeId, ReviewPeriod);
```

### 3.7 Entity-Relationship Diagram

```
AspNetUsers (Id PK)
    │  1
    │  ↕ (UserId FK, one-to-one, SET NULL on delete)
    │  1
Employees (Id PK)
    │  ManagerId → Employees(Id)   [Self-reference, org chart tree]
    │
    ├──1──< Tasks [AssignedById]   (Employee created the task)
    ├──1──< Tasks [AssignedToId]   (Employee assigned to do the task)
    │
    ├──1──< TaskComments [EmployeeId]
    ├──1──< TaskAttachments [EmployeeId]
    │
    ├──1──< TaskReviews [RevieweeId]  (This employee is being reviewed)
    └──1──< TaskReviews [ReviewerId]  (This employee submitted the review)

Tasks (Id PK)
    ├──1──< TaskComments [TaskId]
    └──1──< TaskAttachments [TaskId]
```

## 4. Authentication & Security Flow

### 4.1 Login Flow (step-by-step)

```
Browser                        React Frontend               ASP.NET Core Backend
  |                                 |                               |
  | User submits email+password     |                               |
  |──────────────────────────────→  |                               |
  |                                 | POST /api/auth/login          |
  |                                 |──────────────────────────────→|
  |                                 |                               | 1. UserManager.FindByEmailAsync()
  |                                 |                               | 2. UserManager.CheckPasswordAsync()
  |                                 |                               | 3. UserManager.GetRolesAsync()
  |                                 |                               | 4. Load Employee row (JOIN on UserId)
  |                                 |                               | 5. TokenService.GenerateToken()
  |                                 |                               |    → Creates JWT with claims:
  |                                 |                               |      sub, email, role, employeeId
  |                                 |                               | 6. Set HttpOnly cookie: ws_auth_token
  |                                 |                               | 7. Set non-HttpOnly cookie: XSRF-TOKEN
  |                                 |    200 OK + { user }          |
  |                                 |←──────────────────────────────|
  |  Cookies set by browser         |                               |
  |←────────────────────────────────|                               |
  | AuthContext.login(user)         |                               |
  | → setUser(user)                 |                               |
  | → redirect to /dashboard        |                               |
```

### 4.2 JWT Token Claims

Every JWT contains these claims (read by `UserExtensions.cs`):

| Claim | Value | Used by |
|---|---|---|
| `sub` / `ClaimTypes.NameIdentifier` | ASP.NET Identity `User.Id` (GUID string) | `AuthController.GetCurrentUser()` |
| `ClaimTypes.Role` | `"Admin"` or `"Employee"` | Policy guards (`[Authorize(Policy = ...)]`) |
| `ClaimTypes.Email` | User email | Display only |
| `ClaimTypes.Name` | Full name | Display only |
| `"employeeId"` (custom claim) | `Employee.Id` (integer) | `User.GetEmployeeId()` extension — used everywhere for data scoping |
| `jti` | Random GUID | Uniqueness per token |

### 4.3 How the Cookie Works on Subsequent Requests

The `OnMessageReceived` JWT event in `Program.cs` intercepts every incoming request:

```csharp
// Program.cs — JWT Bearer Events
OnMessageReceived = context => {
    if (context.Request.Cookies.TryGetValue("ws_auth_token", out var token))
        context.Token = token;   // The browser cookie becomes the bearer token
    return Task.CompletedTask;
}
```

This means the client never manually sets an `Authorization: Bearer` header. The browser cookie is sent automatically with every request because `credentials: 'include'` is set in the `apiFetch` helper.

### 4.4 CSRF Protection

Every mutating request from the frontend reads the `XSRF-TOKEN` cookie (readable by JS because `HttpOnly = false`) and sets it in the `X-XSRF-TOKEN` header. The ASP.NET middleware verifies header matches the server's stored antiforgery token.

## 5. Role System — How Roles Work

There are exactly **two roles**: `Admin` and `Employee`.

### 5.1 Roles in the Database

Roles are seeded by `DatabaseSeeder.SeedDatabaseAsync()` at startup into `AspNetRoles`:

```sql
-- After seeding:
SELECT * FROM AspNetRoles;
-- Id | Name     | NormalizedName
-- -- | -------- | ---------------
-- .. | Admin    | ADMIN
-- .. | Employee | EMPLOYEE
```

User-role assignments live in `AspNetUserRoles`:

```sql
SELECT u.Email, r.Name AS Role
FROM AspNetUsers u
JOIN AspNetUserRoles ur ON u.Id = ur.UserId
JOIN AspNetRoles r       ON r.Id = ur.RoleId;
```

### 5.2 How Roles are Checked in Code

**Route-level policy (coarse-grained):**

```csharp
// Only Admin can call this endpoint
[Authorize(Policy = AuthConstants.Policies.RequireAdminRole)]
[HttpPost]
public async Task<IActionResult> CreateEmployee(...)
```

**Helper extensions on `ClaimsPrincipal` (`UserExtensions.cs`):**

```csharp
User.IsAdmin()       // returns true if role claim == "Admin"
User.GetEmployeeId() // parses "employeeId" claim → int?
```

**Resource-based authorization (fine-grained):**
See [Section 12](#12-authorization-handlers--resource-level-rules).

### 5.3 Defined Policies (`AuthConstants.cs`)

| Policy Name | Allowed Roles |
|---|---|
| `RequireAdminRole` | `Admin` only |
| `RequireEmployeeRole` | `Employee` only |
| `RequireAdminOrEmployee` | Both |

### 5.4 Role Capabilities Summary

| Feature | Admin | Employee (Manager) | Employee (No Reports) |
|---|---|---|---|
| Create employee account | ✅ | ❌ | ❌ |
| Create employee profile | ✅ | ❌ | ❌ |
| Edit / deactivate employee | ✅ | ❌ | ❌ |
| See all employees | ✅ | Only self + subordinates + peers | Only self + peers |
| Create task | ✅ (any assignee) | ✅ (subordinates only) | ❌ |
| Edit / delete task | ✅ | ✅ (if they created it and are manager of assignee) | ❌ |
| Update task status (InProgress/InReview) | ✅ | ✅ (if manager of assignee) | ✅ (own tasks only) |
| Mark task Completed | ✅ | ✅ (manager of assignee only) | ❌ |
| Comment on task | ✅ | ✅ (if assignee, creator, or manager) | ✅ (if assignee) |
| Submit review | ✅ (anyone) | ✅ (subordinates only) | ❌ |
| Edit / delete own review | ✅ | ✅ | ❌ |
| View performance page | ✅ | ✅ (self + subordinates) | ✅ (self only) |

## 6. How a User / Employee Account is Created

There are **two separate flows** for creating people in the system. Understanding this is critical.

### 6.1 Flow A — Admin Creates Employee Account (with login credentials)

**When:** Admin goes to `/admin/employees/create-account` and fills in the form.

**Frontend call:**
```ts
// authService.ts
authService.createEmployeeAccount(data)
// → POST /api/auth/employees   (body: CreateEmployeeAccountRequest)
```

**Backend endpoint:** `POST /api/auth/employees` in `AuthController.cs`
- Requires `[Authorize(Policy = RequireAdminRole)]`

**What happens inside `AuthService.CreateEmployeeAccountAsync()`:**

```
1. Validate email doesn't already exist in Employees table
2. Validate email doesn't already exist in AspNetUsers table
3. Validate the ManagerId refers to an active employee
4. BEGIN TRANSACTION
   a. Create ApplicationUser (AspNetUsers row) with the provided email + password
   b. Add "Employee" role to the user (AspNetUserRoles row)
   c. Create Employee row linked via UserId = new user's GUID
5. COMMIT TRANSACTION
```

**SQL written:**
```sql
-- Step a:
INSERT INTO AspNetUsers (Id, UserName, Email, EmailConfirmed, PasswordHash, ...)
VALUES (NEWID(), @email, @email, 1, @hashedPassword, ...);

-- Step b:
INSERT INTO AspNetUserRoles (UserId, RoleId) VALUES (@newUserId, @employeeRoleId);

-- Step c:
INSERT INTO Employees (FirstName, LastName, Email, PhoneNumber, JobTitle, Department,
                       HireDate, Salary, IsActive, CreatedAt, ManagerId, UserId)
VALUES (@fn, @ln, @email, @phone, @title, @dept, @hireDate, @salary, 1, GETUTCDATE(), @managerId, @newUserId);
```

The returned response includes a `UserResponseDto` with the newly created user's data, confirming success on the frontend.

### 6.2 Flow B — Admin Creates Employee Profile Only (no login)

**When:** Admin goes to `/admin/employees` and adds a bare employee profile.

**Frontend call:**
```ts
// employeeService.ts
employeeService.create(data)
// → POST /api/employees   (body: CreateEmployeeRequest)
```

**Backend endpoint:** `POST /api/employees` in `EmployeesController.cs`
- Requires `[Authorize(Policy = RequireAdminRole)]`

This creates only the `Employees` row. No `AspNetUsers` row is created. `UserId` remains `NULL`. The person cannot log in until Flow A is performed.

### 6.3 Seed Data (auto-created at first startup)

`DatabaseSeeder.SeedDatabaseAsync()` runs in `Program.cs` before accepting any HTTP requests. It creates:

## 7. Admin Workflow — What an Admin Can Do

An admin logs in at `/login/admin` and is redirected to `/admin/dashboard` after successful login.

### 7.1 Admin Dashboard (`/admin/dashboard`)

`AdminDashboardPage.tsx` renders:
- Task statistics cards (counts by status)
- Recent activity feed
- Quick links to employees and tasks

Data comes from `GET /api/tasks` (admin gets all tasks) and `GET /api/employees` (admin gets all employees).

### 7.2 Employee Management (`/admin/employees`)

`AdminEmployeesPage.tsx` calls `employeeService.getAll()` → `GET /api/employees`.

Admin can:
- **View** all employees with their manager, department, status
- **Edit** an employee: `employeeService.update(id, data)` → `PUT /api/employees/{id}`
- **Toggle active/inactive**: `employeeService.toggleActive(id, bool)` → `PATCH /api/employees/{id}/active`
- **Deactivate** (soft-delete): `employeeService.deactivate(id)` → `DELETE /api/employees/{id}`
  - This sets `IsActive = false`, not a physical row delete
- **Navigate to create account**: links to `/admin/employees/create-account`

### 7.3 Create Employee Account (`/admin/employees/create-account`)

`AdminCreateEmployeeAccountPage.tsx` collects: name, email, password, phone, job title, department, hire date, salary, and **which manager** to assign.

Calls `authService.createEmployeeAccount(data)` → `POST /api/auth/employees`.

This runs **Flow A** from Section 6.1 (creates both login account and employee profile atomically).

### 7.4 Task Management — Admin View (`/admin/tasks`)

`AdminTaskListPage.tsx` calls `taskService.getAll()` → `GET /api/tasks`.

Admin sees **all tasks in the system** (no data scoping).

Admin can:
- Filter/search tasks by status, priority, assignee
- Open task detail dialog (`TaskDetailDialog.tsx`) to see comments and attachments
- Create a new task: navigate to `/admin/tasks/create`
- Edit a task: `taskService.update(id, data)` → `PUT /api/tasks/{id}`
- Delete a task: `taskService.delete(id)` → `DELETE /api/tasks/{id}`
- Change task status: `taskService.updateStatus(id, { status })` → `PATCH /api/tasks/{id}/status`
- Add comment: `taskService.addComment(taskId, content)` → `POST /api/tasks/{taskId}/comments`

### 7.5 Create Task (`/admin/tasks/create`)

`AdminCreateTaskPage.tsx` → calls `taskService.create(data)` → `POST /api/tasks`.

Admin can assign to **any active employee**.

### 7.6 Reviews Management (`/admin/reviews`)

`AdminReviewsPage.tsx` calls `reviewService.getAll()` → `GET /api/reviews`.

Admin sees all reviews. Admin can:
- Create a review for any employee: `reviewService.create(data)` → `POST /api/reviews`
- Edit their own (or any, since admin): `reviewService.update(id, data)` → `PUT /api/reviews/{id}`
- Delete: `reviewService.delete(id)` → `DELETE /api/reviews/{id}`

## 8. Employee Workflow — What an Employee Can Do

An employee logs in at `/login/employee` and is redirected to `/dashboard`.

### 8.1 Employee Dashboard (`/dashboard`)

`DashboardPage.tsx` shows:
- Greeting banner with their name and role
- Task statistics card (`TaskStatCard`) — counts tasks assigned to them
- Recent activity

Data: `GET /api/tasks` returns only tasks where `AssignedToId == currentEmpId` OR `AssignedById == currentEmpId` OR the task belongs to a subordinate.

### 8.2 My Tasks (`/tasks`)

`TasksPage.tsx` calls `taskService.getAll()`.

**Data scoping in `GET /api/tasks` for non-admins:**

```csharp
// TasksController.cs
if (!isUserAdmin)
{
    var subordinateIds = await _hierarchyService.GetSubordinateIdsAsync(currentEmpId);

    if (subordinateIds.Count > 0)
    {
        // Manager: see own tasks + tasks of all subordinates
        query = query.Where(t =>
            t.AssignedToId == currentEmpId ||
            t.AssignedById == currentEmpId ||
            subordinateIds.Contains(t.AssignedToId.Value));
    }
    else
    {
        // Leaf employee: see only own tasks
        query = query.Where(t =>
            t.AssignedToId == currentEmpId ||
            t.AssignedById == currentEmpId);
    }
}
```

**What an employee can do on their tasks:**
- **View** tasks assigned to them
- **Update status** to `InProgress` or `InReview` (they cannot mark it `Completed`)
- **Add comments** on their own tasks
- **Upload attachments** (up to 25 MB per file)

### 8.3 Performance Page (`/performance`)

`PerformancePage.tsx` calls `reviewService.getAll()` and optionally `reviewService.getEmployeePerformance(id)`.

The employee sees reviews written **about them**:

```sql
-- Equivalent SQL for GET /api/reviews (non-admin, non-manager)
SELECT * FROM TaskReviews
WHERE RevieweeId = @currentEmpId   -- reviews written about me
   OR ReviewerId = @currentEmpId;  -- reviews I wrote (if any)
```

### 8.4 Settings (`/settings`)

`SettingsPage.tsx` — calls `authService.changePassword(...)` → `POST /api/auth/change-password`.

## 9. Task Management — Full Lifecycle

### 9.1 Task Creation (Manager/Admin only)

```
1. Creator fills form in AdminCreateTaskPage or TasksPage (manager role)
2. Frontend: POST /api/tasks  { name, description, assignedToId, dueDate, priority }
3. Backend validates:
   - assignedToId must refer to an active employee
   - If not admin: creator must be a manager OF that employee (HierarchyService.IsSubordinateAsync)
4. INSERT INTO Tasks (..., Status='Pending', CreatedDate=GETUTCDATE())
5. Return 201 Created with full TaskResponseDto (includes assignee name, creator name)
```

### 9.2 Status Update Flow

```
Assignee or Manager updates status:
  PATCH /api/tasks/{id}/status   body: { "status": "InProgress" }

Authorization rules (TaskAuthorizationHandler):
  - Marking Completed  → only manager of assignee (or admin)
  - Other statuses     → assignee OR manager of assignee (or admin)

SQL:
  UPDATE Tasks SET Status = @newStatus, UpdatedDate = GETUTCDATE()
  WHERE Id = @id;
```

### 9.3 Comments Flow

```
Any eligible user (assignee, creator, manager) adds comment:
  POST /api/tasks/{id}/comments  body: { "content": "..." }

INSERT INTO TaskComments (TaskId, EmployeeId, Content, CreatedDate)
VALUES (@taskId, @currentEmpId, @content, GETUTCDATE());

Edit own comment:
  PATCH /api/tasks/{id}/comments/{commentId}
  → Only the author or admin; UPDATE TaskComments SET Content=@new, UpdatedDate=NOW()

Delete own comment:
  DELETE /api/tasks/{id}/comments/{commentId}
  → Only the author or admin
```

### 9.4 Attachments Flow

```
POST /api/tasks/{id}/attachments  (multipart/form-data, file field)
  → Max 25 MB
  → File saved to: wwwroot/attachments/{taskId}/{Guid}{ext}
  → INSERT INTO TaskAttachments (..., Location='/attachments/{id}/{storedName}', ...)

DELETE /api/tasks/{id}/attachments/{attachmentId}
  → Deletes physical file from disk
  → DELETE FROM TaskAttachments WHERE Id = @attachmentId
```

### 9.5 Task Status State Machine

```
                     ┌─────────────────────────────────────────┐
                     ↓                                         |
[Pending] → [InProgress] → [InReview] → [Completed]           |
    ↓             ↓             ↓                              |
    └─────────────┴─────────────┴──→  [Cancelled]             |
                                                               |
  Any status can jump to Cancelled (admin or manager)         ↑
  Completed can only be set by manager of assignee or admin ──┘
```

## 10. Performance Reviews — Full Lifecycle

### 10.1 Creating a Review

**Who can review whom:**
- **Admin** → any active employee
- **Manager (non-admin employee with subordinates)** → only their direct or indirect reports

```
Frontend: POST /api/reviews
Body: { revieweeId, starRating, comment, reviewPeriod }

Backend (ReviewsController.CreateReview):
  1. Get currentEmpId from JWT claims
  2. If not admin: HierarchyService.IsSubordinateAsync(currentEmpId, request.RevieweeId)
     → Traverses upward from reviewee to see if currentEmp is in the chain
     → If not subordinate → 403 Forbidden
  3. Validate reviewee is active
  4. INSERT INTO TaskReviews (RevieweeId, ReviewerId, StarRating, Comment, ReviewPeriod, CreatedAt)
     VALUES (@revieweeId, @currentEmpId, @rating, @comment, @period, GETUTCDATE());
  5. Return 201 Created with ReviewResponseDto
```

### 10.2 Reading Reviews

**GET /api/reviews** (with optional `?revieweeId=X` filter):

```csharp
// ReviewsController — data scoping for non-admins
query = query.Where(r =>
    r.RevieweeId == currentEmpId ||      // reviews about me
    r.ReviewerId == currentEmpId ||      // reviews I wrote

```

**GET /api/reviews/performance/{employeeId}** — full performance summary:


## 11. Hierarchy Service — How the Org Tree Works in Code

`HierarchyService.cs` is the core of all manager-subordinate logic. It is injected everywhere authorization scoping is needed.

### 11.1 `GetSubordinateIdsAsync(managerEmployeeId)`

Returns **all** employee IDs under a given manager, recursively (BFS traversal):

```csharp
// 1. Load all active employees (Id, ManagerId) into memory
var activeEmployees = await _dbContext.Employees
    .Where(e => e.IsActive)
    .Select(e => new { e.Id, e.ManagerId })
    .ToListAsync();

// 2. Build lookup: managerId → [directReportIds]
var lookup = activeEmployees
    .Where(e => e.ManagerId.HasValue)
    .ToLookup(e => e.ManagerId!.Value, e => e.Id);

// 3. BFS from the given manager down the tree
var queue = new Queue<int>();
queue.Enqueue(managerEmployeeId);
while (queue.Count > 0) {
    var current = queue.Dequeue();
    foreach (var subordinateId in lookup[current]) {
        subordinates.Add(subordinateId);
        queue.Enqueue(subordinateId);  // go deeper
    }
}
```

**Example org chart:**
```
Sarah (Admin, Id=1)
  └── Alex (Id=2)
        └── Bob (Id=5)
  └── David (Id=3)
  └── Elena (Id=4)

GetSubordinateIdsAsync(1) → [2, 3, 4, 5]
GetSubordinateIdsAsync(2) → [5]
GetSubordinateIdsAsync(3) → []
```

### 11.2 `IsSubordinateAsync(managerEmployeeId, targetEmployeeId)`

Checks if `targetEmployeeId` is **anywhere below** `managerEmployeeId` in the chain. This walks **upward** from the target:

```
target.ManagerId == managerId?  → YES → true
  else: target.Manager.ManagerId == managerId? → ...etc
```

Protects against cycles with a `HashSet<int> visited`.

### 11.3 `IsManagerAsync(employeeId)`

Simple check: does anyone have this employee as their `ManagerId`?

```sql
SELECT COUNT(1) FROM Employees WHERE ManagerId = @employeeId AND IsActive = 1
```

## 12. Authorization Handlers — Resource-Level Rules

These are `IAuthorizationHandler` implementations that the ASP.NET DI container calls when `_authorizationService.AuthorizeAsync(User, resource, operation)` is invoked.

### 12.1 `TaskAuthorizationHandler`

Handles: `Read`, `Create`, `UpdateStatus`, `Complete`, `Edit`, `Delete`, `Comment` operations on `WorkTask`.

```
Admin → always passes all operations.

Non-admin variables computed per request:
  isAssignee        = task.AssignedToId == currentEmpId
  isCreator         = task.AssignedById == currentEmpId
  isManagerOfAssignee = HierarchyService.IsSubordinateAsync(currentEmpId, task.AssignedToId)

Operation rules:
  Read          → isAssignee OR isCreator OR isManagerOfAssignee
  Complete      → isManagerOfAssignee ONLY  (strict sign-off: manager confirms done)
  UpdateStatus  → isAssignee OR isManagerOfAssignee
  Comment       → isAssignee OR isCreator OR isManagerOfAssignee
  Edit/Delete   → isCreator AND isManagerOfAssignee  (must be both creator AND manager)
```

### 12.2 `EmployeeAuthorizationHandler`

Handles: `Read`, `Manage` operations on `Employee`.

```
Admin → always passes.

Non-admin rules:
  Read self    → always allowed (resource.Id == currentEmpId)
  Subordinate  → HierarchyService.IsSubordinateAsync(currentEmpId, resource.Id) → allowed
  Peer         → same direct manager → allowed for Read only
```

### 13.1 Route Structure (`AppRoutes.tsx`)

```
/admin/dashboard        → AdminDashboardPage   [requiredRole="Admin"]

/admin/employees/create-account → AdminCreateEmployeeAccountPage [Admin]
/admin/tasks            → AdminTaskListPage    [requiredRole="Admin"]
/admin/tasks/create     → AdminCreateTaskPage  [requiredRole="Admin"]
/admin/reviews          → AdminReviewsPage     [requiredRole="Admin"]
/admin/settings         → AdminSettingsPage    [requiredRole="Admin"]
```

### 13.2 `ProtectedRoute` Component

```tsx
// ProtectedRoute.tsx
export default function ProtectedRoute({ requiredRole }) {
  const { isAuthenticated, role, isLoading } = useAuth();

  if (isLoading) return <LoadingSpinner />;
  if (!isAuthenticated) return <Navigate to="/login" />;
  if (requiredRole && role !== requiredRole)
    return <Navigate to={role === 'Admin' ? '/admin/dashboard' : '/dashboard'} />;
  return <Outlet />;
}
```

If a logged-in employee tries to visit `/admin/dashboard`, they are silently redirected to `/dashboard`, and vice versa.

### 13.3 `AuthContext` — Session Persistence

On first load, `AuthProvider` calls `authService.getCurrentUser()` → `GET /api/auth/me`. If the `ws_auth_token` cookie is still valid, the backend returns the user and the app stays logged in. If the cookie expired or is missing, the user is redirected to `/login`.

```tsx
// AuthContext.tsx
useEffect(() => {
  validateSession(); // calls GET /api/auth/me
}, []);
```

### 13.4 `GuestRoute` Component

Wraps all login/forgot-password routes. If the user is already authenticated, they are redirected away (back to their dashboard). This prevents logged-in users from seeing the login form.

## 15. End-to-End Flow Diagrams

### 15.1 Login Flow

```
flowchart TD
    A[User opens app] --> B{Has ws_auth_token cookie?}
    B -- No --> C[Redirect to /login]
    B -- Yes --> D[GET /api/auth/me]
    D --> E{Token valid?}
    E -- Yes --> F[AuthContext: setUser]
    E -- No --> C
    F --> G{User role?}
    G -- Admin --> H[/admin/dashboard]
    G -- Employee --> I[/dashboard]
    C --> J[User fills login form]
    J --> K[POST /api/auth/login]
    K --> L{Credentials valid?}
    L -- No --> M[Show error]
    L -- Yes --> N[Set HttpOnly cookie + CSRF cookie]
    N --> G
```

### 15.2 Task Creation & Completion Flow

```
flowchart TD
    A[Admin/Manager creates task] --> B[POST /api/tasks]
    B --> C{Caller is admin?}
    C -- Yes --> D[Assign to anyone]
    C -- No --> E{Assignee is subordinate?}
    E -- No --> F[403 Forbidden]
    E -- Yes --> D
    D --> G[INSERT Tasks WHERE Status=Pending]
    G --> H[Assignee sees task on /tasks]
    H --> I[Assignee updates status → InProgress]
    I --> J[PATCH /api/tasks/id/status]
    J --> K[Assignee marks InReview]
    K --> L[Manager sees InReview task]
    L --> M[Manager marks Completed]
    M --> N{Caller is manager of assignee?}
    N -- No --> O[403 Forbidden]
    N -- Yes --> P[UPDATE Tasks SET Status=Completed]
```

### 15.3 Employee Account Creation Flow

```
flowchart TD
    A[Admin fills create-account form] --> B[POST /api/auth/employees]
    B --> C{Email unique in Employees + AspNetUsers?}
    C -- No --> D[400 Bad Request]
    C -- Yes --> E{ManagerId is active employee?}
    E -- No --> F[400 Bad Request]
    E -- Yes --> G[BEGIN TRANSACTION]
    G --> H[INSERT AspNetUsers]
    H --> I[INSERT AspNetUserRoles with Employee role]
    I --> J[INSERT Employees linked to new UserId]
    J --> K[COMMIT]
    K --> L[Return UserResponseDto to Admin]
```

### 15.4 Review Submission Flow

```
flowchart TD
    A[Manager opens Reviews page] --> B[GET /api/reviews]
    B --> C[See reviews of team]
    C --> D[Click: Submit Review for subordinate]
    D --> E[POST /api/reviews body: revieweeId, rating, comment, period]
```
